# cp-self: Jeremy's Operating Manual, Portable

A profile of how Jeremy works, thinks, and decides - extracted 2026-07-16 by Claude Fable 5 from chat histories, learning guides, project docs, plans, and memory files.
Same idea as [cp-fable](../cp-fable): that repo captures how the model should work; this one captures who it is working with.
Injected into `CLAUDE.md` so every session starts already knowing where Jeremy is strong, where he needs backup, and when to push back.

## Contents

| File             | What it is                                                                  |
|------------------|-----------------------------------------------------------------------------|
| `self-manual.md` | The asset. Jeremy's strengths, gaps, intuition map, and how to support him. |
| `SCAN_LOG.md`    | Every file read during extraction, grouped by source.                       |
| `install.sh`     | Idempotent installer. Copies the manual + adds one import line.             |

`self-manual.md` and `SCAN_LOG.md` are gitignored (personal profile data stays out of git); they live only on this machine, regenerated by the re-extraction prompt below.

## Re-extraction

Rerun when enough new history has accumulated (a few months of sessions) or after a major shift in how you work.
Consider running it in a session without `CLAUDE.md` loaded (`claude --setting sources` tricks, or a scratch `CLAUDE_CONFIG_DIR`), so the extractor observes the raw history instead of being steered by the rules you already wrote about yourself.

Prompt:

> Build an operating manual about me - the human - for the models that work with me.
> Scan my Claude Code chat histories (`~/.claude/projects/*/`, user messages only), my memory files, my prompt history, my global CLAUDE.md (each rule I wrote marks a past pain point), all `learning_guide.html` files, and the docs/plans/READMEs of my own git repos.
> Keep the scan non-invasive: `.claude` dirs and project folders (identified by `.git`) only, and log every file you read into `SCAN_LOG.md`.
> From the evidence, not from flattery, extract: 1. What I'm actually good at - where my intuition can be trusted and my pushback is usually right. 2. Where my intuition is unreliable and the model should push back or verify instead of complying. 3. My recurring failure patterns - the things I have to be saved from again and again. 4. How I frame requests, and how to read what I actually need beneath what I typed. 5. What I under-invest in and quietly hope the model covers. 6. How to disagree with me so that it lands. 7. What finished looks like to me, and what I will reject even if it is technically correct.
> For each point: the pattern, the evidence behind it (short verbatim quotes), and the concrete behavior the model should adopt.
> Be honest. A manual that protects my ego is useless. End with a short self-test the model runs before handing me anything.

Then rerun `./install.sh`.

## Install

```bash
./install.sh                    # installs into ~/.claude
./install.sh /path/to/other-dir # if a session uses a non-default CLAUDE_CONFIG_DIR
```

Machine 2:

```bash
scp -r ~/create/cp-self othermachine: && ssh othermachine 'cd cp-self && ./install.sh'
```

## Verify the transplant took

```bash
claude -p "What should you watch out for when I hand you a plan I'm excited about?"
```

Pass: it answers from the manual's intuition map (specific to Jeremy, not generic advice).
Fail: generic "communicate clearly" boilerplate - tighten the manual and reinstall.
